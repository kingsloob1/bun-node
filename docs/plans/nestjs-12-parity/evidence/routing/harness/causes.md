## Causes of every "bun differs" row (hand-written; `harness/causes.md`)

Our code is cited at develop `73bf4a00` (the worktree `bun-node-nest12-ae-1015`; the mirrors' `packages/*/lib` are byte-identical to it, checked with `diff -rq`). Nest is cited by short commit from the `nest-src` clone and by `file:line` in the mirrors' `node_modules` (12.1.3 unless said otherwise).

### D1. `@QueryMethod` fails the whole application on Nest 12 (all 4 rows of `query-method`: QUERY /q, GET /q, GET /gq) — regression in bun on 12

- **What:** `NestFactory.create` → `listen` throws `TypeError: this.instance.query is not a function`; every route of the app is lost, not just the QUERY one. Express answers `QUERY /q` with 200.
- **Cause:** the router explorer resolves the verb with `RouterMethodFactory`, which maps `RequestMethod.QUERY` to `'query'` (`@nestjs/core/helpers/router-method-factory.js:19`), so it calls the adapter's `query()`. `BunHttpAdapter` does not define one, so `AbstractHttpAdapter.query()` runs, which delegates to `this.instance.query(...)` (`@nestjs/core/adapters/http-adapter.js:129-130`); `BunRouter` has no `query` method (the adapter's verb list is `BunHttpAdapter.ts:1586-1604`; `getRequestMethodStr` has no `QUERY` case, `BunHttpAdapter.ts:3264-3359`, so `forRoutes({ method: RequestMethod.QUERY })` middleware would throw `InternalServerErrorException` there too). `RequestMethod.QUERY`/`@QueryMethod` arrived in 11.2.0 and 12.0.0 (#17162, `eac10cd2d`); develop's Nest 11 pin is 11.1.27, which predates it.
- **Fix:** a `query` verb on `BunRouter` (routejs has no QUERY: register through `setRoute` with `method: "QUERY"`, like the `proppatch` shim at `BunRouter.ts:3160-3162`), a `query` override on `BunHttpAdapter` beside the other verbs, the generated typed overloads for it, and a `RequestMethod.QUERY → "query"` case in `getRequestMethodStr`. `QUERY` on `@All` already works on both adapters (row "QUERY on @All"), so Bun.serve accepts the method.

### D2. A param that cannot be decoded answers 500 instead of 400 on Nest 12 (1 row, `GET /users/%E0%A4%A`) — regression in bun on 12

- **What:** Express (11 and 12) and bun@11: `400 "Failed to decode param '%E0%A4%A'"`. bun@12: `500 "Internal server error"`, and `ExceptionsHandler` logs the error twice.
- **Cause:** our router raises Express 5's error, a `URIError` with `status: 400` (`BunRouter.ts:144-148`, passed to `next` at `BunRouter.ts:5213`). On Nest 11 the core mapped it: `RoutesResolver.mapExternalException` turns `SyntaxError`/`URIError` into `BadRequestException` (`repo11/node_modules/@nestjs/core/router/routes-resolver.js:84-87,94-100`). Nest 12 moved that mapping into the adapter (#15075, `07603b53f`, first in v12.0.0): the exception layer now throws `httpAdapter.mapException(err)` (`@nestjs/core/router/routes-resolver.js:94-96`), `AbstractHttpAdapter.mapException` returns the error unchanged (`@nestjs/core/adapters/http-adapter.js:229-231`), and only `ExpressAdapter.mapException` (`express-adapter.js:442-451`) maps `SyntaxError`/`URIError` to `BadRequestException`. `BunHttpAdapter` has no `mapException`, so `BaseExceptionFilter` sees an unknown error (its `isHttpError` wants `statusCode`, not `status`) and answers 500.
- **Fix:** override `mapException` in `BunHttpAdapter` as Express's does (`SyntaxError`/`URIError` → `BadRequestException(error.message)`). The same gap covers a `SyntaxError` from an invalid JSON body, which this harness does not send (the existing `expressCompat` "invalid JSON" probe does).

### D3. Path syntax: our router is not path-to-regexp 8 (15 rows on both versions, plus 7 in the Nest-12-only groups) — bun differs from express (11 and 12)

Nest hands the adapter Express 5 (path-to-regexp 8) paths; `BunRouter` compiles them with `@routejs/router` 3.0.3, whose syntax is path-to-regexp-1-style (`*` is `(.*)`, `:x?` optional, `{`/`}` literal: `node_modules/@routejs/router/src/path-regex.mjs:15-27`). The only translation is `normalizeCatchAllPath` (`BunRouter.ts:220-231`, applied in `setRoute`, `BunRouter.ts:1216-1227`), which turns both `*name` and `{*name}` into routejs's bare `*`. Consequences:

- **D3a. Wildcard params are a string, not an array** (`/files/a/b/c`, `/files/a%2Fb`, `/files2/x/y`, `/files/a/b` excluded, `/files/a` in mw-basic, `/s/a/b`, `/s/a/z`, `/s/x/y/z` ×3 groups): Express gives `{ path: ["a","b","c"] }` (path-to-regexp 8 splits a wildcard on `/` and decodes each segment, so `a%2Fb` → `["a/b"]`); we give `{ "0": "a/b/c", path: "a/b/c" }` — the positional key plus the name alias, one decoded string (`BunRouter.ts:4922-4948`). A controller doing `@Param('path') p: string[]` breaks.
- **D3b. `*name` matches an empty tail** (`GET /files/` → 200 here, 404 on Express; the `MwStarPath` entry in `GET /api/` in mw-prefix): in path-to-regexp 8, `*name` needs at least one character and only `{*name}` is optional; collapsing both to `*` makes them the same.
- **D3c. Optional groups do not exist** (`/opt`, `/opt/1`, `/opt/` → 404 here, 200 on Express): `opt{/:x}` reaches routejs verbatim, where `{` is a literal, so the route can never match — and nothing fails at startup.
- **D3d. Legacy paths are not converted, and no warning is logged** (`/legacy/a/b`, `/legacy/`, `/legacy/*`, `/old/x/y`, `/old/(.*)`): Express's adapter overrides `normalizePath` to run `LegacyRouteConverter.tryConvert` (logging the "Unsupported route path … Attempting to auto-convert" warning) and to validate with `pathToRegexp` (`express-adapter.js:194-206`); the core calls it per route (`@nestjs/core/router/router-explorer.js:105-106`). `BunHttpAdapter` does not override it, so `AbstractHttpAdapter.normalizePath` returns the path unchanged (`http-adapter.js:179-181`) and routejs's own `*`/`(.*)` match the same requests with positional params (`{ "0": "a/b" }` against Express's `{ path: ["a","b"] }`) and no warning. The status codes agree on every legacy probe; the params do not.
- **Fix (one change for D3a–d):** give `BunHttpAdapter` a `normalizePath` that does what Express's does (convert legacy paths with `LegacyRouteConverter` from `@nestjs/core/internal` on 12 / `@nestjs/core/router/legacy-route-converter` on 11, so the warning is logged; validate with `path-to-regexp`), and make `BunRouter` match path-to-regexp 8 semantics: either compile route paths with `path-to-regexp` 8 itself (already in the tree as Express's dependency) or translate `{…}` optional groups, keep `*name` non-empty, and publish wildcard params as `string[]`. Changing the param shape is a breaking change for direct `BunRouter` users of `req.params[0]`; bun-common's own Express-5 claim says it should be the array.

### D4. Routes are case-sensitive by default (2 rows, `/case`, `/CASE`) — bun differs from express (11 and 12)

- **What:** `@Get('Case')` answers `/case` and `/CASE` on Express; 404 here.
- **Cause:** `BunHttpAdapter`'s constructor defaults the router to `caseSensitive: true` (`BunHttpAdapter.ts:279-281`); Express's `case sensitive routing` is off by default (bun-common's `BunRouter` itself defaults to `false`, `BunRouter.ts:1239-1240`).
- **Fix:** default `caseSensitive` to `false` in the adapter (a behaviour change for existing bun-nest users, who can pass `router: { caseSensitive: true }`), or document the deliberate difference in the `expressCompat` KNOWN list.

### D5. `@HostParam` values are lower-cased (1 row, `Host: A.Example.com`) — bun differs from express (11 and 12)

- **What:** Express gives `sub: "A"`, we give `"a"`.
- **Cause:** `getRequestHostname` returns `request.hostname` (`BunHttpAdapter.ts:1334-1336`), which is `new URL(request.url).hostname` (`BunRequest.ts:5138-5140`, `3055-3057`): the WHATWG URL parser lower-cases the host. Express's `req.hostname` is the `Host` header as sent, minus the port. Both match the host pattern case-sensitively, so a pattern with capitals (`{ host: 'API.:x.example.com' }`) would also stop matching here.
- **Fix:** derive the hostname from the `Host` header (strip the port, keep the case) for `getRequestHostname`, as Express does; leave `BunRequest.hostname` alone or change it with a changelog entry.

### D6. Wildcard middleware does not run on the bare global prefix (1 row, mw-prefix `GET /api`) — Nest 12 changed Express, bun kept 11's answer

- **What:** with `setGlobalPrefix('api')` and `forRoutes('*')`, Express on 12 runs the middleware on `GET /api` (#17942, `82a77eb53`, first in v12.1.3); we do not (nor did either adapter on 11).
- **Cause:** for a wildcard route the core registers `"<prefix>$"` beside `"<prefix>/{*path}"`, the `$` meaning "exact match" (`@nestjs/core/middleware/route-info-path-extractor.js:30,35`, the same on 11.1.27). Express's `createMiddlewareFactory` now strips the `$` and registers the path as an exact `all()` route that skips a trailing-slash request (`express-adapter.js:258-286`). `BunHttpAdapter.createMiddlewareFactory` passes the path through unchanged to `useMethod` (`BunHttpAdapter.ts:3361-3378`), so the middleware is mounted at the literal path `/api$`, which no request reaches.
- **Fix:** in `createMiddlewareFactory`, strip a trailing `$` and register an exact (non-prefix) method route for it whose handler calls `next()` when `req.path` ends with `/`, as Express's does.

### D7. Not-found outside the global prefix (3 rows, `/nope` and `/apiary` with a prefix) — Nest 12 changed Express, bun kept 11's answer

- **What:** with a global prefix, Express on 12 answers an unknown path *outside* the prefix with Express's own `finalhandler` page (`404`, `text/html`, `<pre>Cannot GET /nope</pre>`), not Nest's JSON 404: Nest's not-found handler is now mounted only under the prefix and on the excluded routes' exact paths (`express-adapter.js:147-181`; prefix scoping from `33f37d627`, first in v12.0.0, normalised by #17648 `ab64da77f`, excluded routes by #17923 `529152191`, v12.1.3). We keep answering Nest's JSON 404 everywhere, as both adapters did on 11.
- **Cause:** `setNotFoundHandler(handler, _prefix)` ignores the prefix and the new third argument `excludedRoutes` (`BunHttpAdapter.ts:1302-1307`); the handlers run for every request no route took (`#respond`, `BunHttpAdapter.ts:510-530`).
- **Fix / decision:** to match, scope the not-found handlers to the prefix and the excluded paths and answer everything else with the adapter's own bare 404 (a `finalhandler`-style HTML page, as `handleRequestError` already produces for errors). Matching costs users Nest's JSON 404 (and their exception filters) outside the prefix, which may be worse than the difference; the plan should decide, and either way record it. Method misses on excluded routes (#17923's case) already match: 404 JSON on both.

### D8. bun-common's `routeSpecificity` on top of Nest (4 rows: `GET /ag` in both `+bun-routeSpecificity` groups, `/s/me` and `/s/a/b` without Nest's strategy) — opt-in only

- **What:** with bun-common's own `routeSpecificity: true`, `@All()` declared before `@Get()` on one path loses to the `@Get()` (Express, and Nest's sorter, keep declaration order: `ag.all`). Without Nest's `specificity` strategy, it also reorders `/s/me` and `/s/a/b` (2 more rows in `n12-declaration+bun-routeSpecificity`), which is what that option is for.
- **Cause:** `BunRouter`'s ranking puts an exact method match ahead of `all` (`routeSpecificityIteratees`, `BunRouter.ts:4968-5005`), a criterion Nest's `RouteSpecificitySorter` does not have (it ranks path segments only, ties keep declaration order: `@nestjs/core/router/route-specificity-sorter.js`).
- **Fix:** none needed for the default (it is off: `BunRouter.ts:1092`, and the adapter does not turn it on, `BunHttpAdapter.ts:279-284`); document that under Nest 12 `routeResolutionStrategy: 'specificity'` is the supported way, and that adding bun-common's `routeSpecificity` on top re-ranks by method too.

### Not a difference: transport

- `GET //dbl//inner` was a fetch-vs-socket mismatch until the harness sent it over a raw socket: **Bun's `fetch` client sends `http://host//a//b` with the request target `/a//b`** (Node 24's `fetch` sends `//a//b`; `new URL(...).pathname` is `//a//b` in both). Measured in `agent-routing/scratch/dblslash.ts` and `dbl-node.mjs`. A candidate Bun bug (not filed: this task posts nothing).
- `x-powered-by: Express` is sent by Express and not by us on every request (not compared).

## What Nest 12 changed, seen on both adapters

- **`exclude({ path, method: GET })` now also excludes `HEAD`** (mw-basic `HEAD /gonly`: `MwCtrl` ran on 11, not on 12; #17950, `2e4dea33b`, v12.1.3). Both adapters follow, because the check is in the core.
- **Middleware for a controller whose path carries slashes** (`@Controller('/slash/')` + `@Get('/x')`, `forRoutes(SlashController)`): the middleware did not run on 11, runs on 12 (#18075, `f1a4d3017`, v12.1.3). Both adapters.
- **A middleware after a transient-scoped one** (`apply(TransientMw, AfterTransient)`): `AfterTransient` was skipped on 11, runs on 12 (#17846, `21648746d`, v12.1.0: the registration loop's `return` on a transient middleware became `continue`, `@nestjs/core/middleware/middleware-module.js:116-118`). The transient middleware itself is never registered on either version, so it is in no trail. Both adapters.
- **`VERSION_NEUTRAL` in a middleware route info** (`forRoutes({ path: 'ver', version: VERSION_NEUTRAL })` under URI versioning): on 11, Express fails to boot (`PathError … /vSymbol(VERSION_NEUTRAL)/ver`), and we boot but register that literal path so the middleware never runs; on 12 both run it on `/ver` (#17947, `e9300535d`, v12.1.3). 5 rows "bun matches on 12 only".
- **Wildcard middleware on the bare prefix** (D6) and **not-found outside the prefix** (D7): Express-only changes, which we do not follow.
- **Exception mapping moved to the adapter** (D2): a core change that only adapters overriding `mapException` survive.
- **`@QueryMethod`** (D1): new verb; breaks our adapter at startup.
- **Unchanged on both:** everything in the versioning tables (URI, HEADER, MEDIA_TYPE, CUSTOM, `defaultVersion`, arrays, `VERSION_NEUTRAL`), the global prefix with its three exclusion forms, HEAD falling back to GET, `@Head`/`@Options`/`@Search`/`@All`, OPTIONS on a GET-only route (Nest's 404 on both: Nest's not-found handler runs before Express's automatic OPTIONS answer), `@Redirect`/`@HttpCode`/`@Header`, host routing, request paths with duplicate slashes. `@Get('a//b')` is registered as `/dbl/a//b` on both versions: #17710 (`1c4d9c42d`, v12.0.2) only changed `normalizePath` for a path *not* starting with `/` (RouterModule paths), which the harness does not use.
- **Array of global prefixes** (#17713, `bfb084384`): reverted by #17845 (`40d07dc62`) in the same release, so no 12.x has it. `setGlobalPrefix(['api','v1'])` on 12.1.3 boots on both adapters without a warning and serves the routes **unprefixed** (`/hello` 200; `/api/hello`, `/v1/hello`, `/api,v1/hello` 404) — the same as on 11, the same on both adapters.

## Nest 12's route options with our adapter

- **Does Nest sort for us? Yes.** `BunHttpAdapter` has no `isRouteOrderSensitive()`, so Nest treats it as order-sensitive (`this.httpAdapter.isRouteOrderSensitive?.() ?? true`, `@nestjs/core/nest-application.js:154`), sorts with `RouteSpecificitySorter` when `routeResolutionStrategy: 'specificity'` (`nest-application.js:155,180-182`) and registers the routes in that order (`nest-application.js:215-219` → `router-explorer.js:164`). `BunRouter` keeps registration order for route handlers unless its own `routeSpecificity` is on, which defaults to off (`BunRouter.ts:1092`) and which the adapter does not set (`BunHttpAdapter.ts:279-284`). Result: **every `n12-specificity` request answers as on Express** (`/s/me` → `me`, `/s/a/b` → `ab`, `/s/a/z` → `aParam`), the params shape (D3a) aside. Express itself declares `isRouteOrderSensitive() { return true; }` (`express-adapter.js:333-335`, #16954 `fcb3d7d3d`); we should declare it too rather than rely on the default.
- **Conflict policy:** identical warnings and the identical `RouteConflictException` on both adapters (`n12-conflict-warn`, `n12-conflict-error`); with `duplicate: 'warn'` the first-declared duplicate wins on both. Because we count as order-sensitive, Nest keeps both duplicates and lets the router pick the first, which ours does.
- **Double sort:** with bun-common's `routeSpecificity: true` as well, path-only orderings agree (Nest's order is the tie-break), but our ranking adds "exact method beats `all`", so `@All` declared before `@Get` diverges (D8).
- **What the detector sees:** it reads each route's *normalised* path (`router-explorer.js:105-106` → `onRouteResolved({ path: normalizedPath })`). With no `normalizePath` override we hand it Nest's own syntax, which it understands (`*name`, `{*name}`, `:param`); a future override that rewrote paths into routejs syntax (bare `*`) would change what it tokenizes, so D3's fix should keep paths in path-to-regexp 8 form at that point and translate later, inside `BunRouter`.
